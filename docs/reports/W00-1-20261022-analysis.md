## 项目理解

QualityOffice AI 是面向专业工作的通用 AI 知识与办公助手。通用产品层不得写死 QA/QC；医药是首个可选领域预设和首批验证市场。产品按底座、知识库、领域资讯、办公产品化、定制调优推进。

V0.1 不能因后续版本规划而删减已确认范围：Windows 10/11 x64 可安装底座、基础任务、七类文件输入、OCR、联网来源、受控基础 Office 副本、邀请账号、模型网关、额度账本、最小后台、更新与诊断。原件保留，所有修改在受控副本和独立产物路径完成。

当前目录是“开发基准包 + 启动流程包”，不是产品仓库。规格包明确声明没有应用实现、真实 Windows 构建或产品测试结果。

## 会影响首阶段落地的问题

### 必须先解决的阻塞

1. **正式产品仓库不存在。**  
   位置/依据：当前目录无 `.git`、无 dsh 源码、无锁文件；`docs/START-HERE.md` 也声明启动包不包含源码。  
   影响：无法冻结上游、保留历史、执行安装/构建或生成真实发行清单；W00-1 不能完成。  
   处理：在同级临时目录克隆官方仓库，创建产品分支并验证历史后，再完整迁入基准资料；禁止对当前非空目录直接 clone 或清空覆盖。

2. **本机无法运行基准结构检查。**  
   位置/依据：`validate_spec.py:11,63,90`；Windows 路径分隔符导致 `contracts/openapi.json` 不进入 `schemas`。  
   影响：根目录和未来 `docs/spec/` 在目标 Windows 环境都不能获得本机结构检查证据。  
   处理：在正式接入时对检查器做最小跨平台修复（相对路径统一为 POSIX 形式），按基准变更规则同步 `PACKAGE-MANIFEST.json` 与 `validation_report.json`，并保留本次失败记录。本轮不修改冻结基准。

3. **候选提交和发行组合尚未冻结。**  
   位置/依据：`baseline/decisions.json` 的 G00 全部为 `null/open`，发行清单仅为模板；当前 `687f...4317` 只是可变 master 的观察值。  
   影响：所有构建、插件、运行时、资产和许可结论都不可作为发行事实。  
   处理：从固定提交检出，执行锁定安装、构建和组件矩阵后再决定冻结；不能直接把本轮 HEAD 写成已通过基线。

4. **Windows 构建前置尚未证明就绪。**  
   位置/依据：官方固定提交打包文档；本机 pnpm 与固定版本不一致，PowerShell 7 缺失，VC workload/SDK 未验证，产品 appId 和 HTTPS 更新策略未冻结。

## W00-1 推荐执行方案

### 仓库接入策略

推荐“同级临时克隆 + 核验后迁入”的保留历史方案：

1. 保留当前目录完整副本和文件 hash，不在非空目录 clone。
2. 在同级临时目录克隆官方仓库；将官方 remote 保留为 `upstream`，产品仓库 remote 待实际托管地址确定后设为 `origin`。
3. 基于经过检查的 40 位候选提交创建产品分支，不以 `master/latest` 作为发行引用。
4. 保留上游根 `AGENTS.md`、README、许可、锁文件和工程配置；把本项目规则合并为不冲突的根规则/目录规则。

不推荐把当前资料目录直接 `git init` 后强行 checkout 上游：根 README、AGENTS 等同名未跟踪文件会与上游冲突，容易覆盖资料或产生无法审查的初始状态。

### 执行步骤

1. **冻结接入输入**：记录当前资料包 hash、官方 URL、候选 40 位提交、上游 tags/发布记录和选择理由。
2. **检出与读规则**：在临时仓库检出候选提交，读取上游及目录级 `AGENTS.md`、根/桌面 package 配置、锁文件、打包和许可说明。
3. **核对构建机**：用官方 packageManager 激活 pnpm 11.28.5，运行 Windows 打包文档给出的配置/工具 `--check`；缺什么只记录什么。
4. **锁定安装**：执行 `pnpm install --frozen-lockfile`；保存提交、根锁文件 SHA256、Node/pnpm/Python/VC/SDK 实际版本和日志。
5. **上游基线检查**：按上游规则运行与桌面候选直接相关的构建/检查；至少完成构建产物与 build check，不能以文档检查代替。
6. **能力缺口矩阵**：逐项核对桌面宿主、会话、Office Skills、Office-to-PDF、文件读取、OCR、联网来源和 Windows 子进程；区分“代码存在”“打包包含”“干净机可运行”。
7. **插件兼容预检**：记录每个候选的 commit、包版本、peer/engine、锁文件、Windows 原生资产、许可证；先用 `dsh-open-file` 的声明不匹配验证 TC-002 拒绝路径。
8. **发行资产与许可**：枚举 Node/Python、wheels、OCR 语言/模型、LibreOffice kit、字体、DLL/EXE、notices 和许可证；未知项保持阻断。
9. **形成交付物**：填写 G00 ADR、实值发行清单草案和集中补丁台账；当前未知的安装包 hash、签名等字段保持未冻结，不能填猜测值。
10. **执行 TC-001—TC-003**：从记录提交重新安装、执行兼容拒绝、人工核对许可与资产；每项保存环境、版本/hash、操作、结果和证据路径。
11. **审查与状态更新**：检查 diff、报告和门槛；只有三条用例均通过且交付物齐全才把 W00-1 标为 `completed`，否则保持 `in_progress` 或 `blocked`。
