# QualityOffice AI 统一审查规则

供开发自检与 Cursor / Codex 独立审查共同使用。与开发 Spec 的完成条件、缺陷级别和当前工作包验收一致。

## 1. 输入和范围

审查前明确工作包、需求/测试编号、基准与目标 commit，以及未提交改动是否在范围内。读取实际 diff、必要上下文、相关契约和验证证据；不凭工具上次的“通过”结论直接认可。

只审查本次改动及其直接影响。与本次无关的历史问题单独记录；确有原件损坏、越权、凭据或系统性账本风险时，说明影响并按 Spec 阻止相关发行。

## 2. 什么可以构成缺陷

至少有一项明确依据：违反需求/契约/完成条件；对具体有效输入会产生错误行为；有可复现步骤或充分代码路径证明；缺少当前版本必需的验证证据。

每条发现包含：位置、触发条件、预期/实际、影响、依据、验证方式和最小修复方向。不能复现的风险标“待验证”，列出如何验证，不冒充已确认 bug。

无缺陷可以明确写“未发现有证据的阻断问题”。审查不设问题数量目标。

## 3. 分级与是否阻断

| 级别 | 判断依据 | 处理 |
| --- | --- | --- |
| S0 | 原件损坏、越权/凭据泄露、系统性超扣或虚构依据 | 阻止相关合并/发行并优先修复 |
| S1 | 核心流程不可用、数据丢失 | 阻断受影响工作包完成与发行 |
| S2 | 局部失败且有替代路径 | 违反当前 P0 或工作包完成条件则阻断，否则记录后续处理 |
| S3 / 建议 | 轻微界面、风格或可选优化 | 非阻断，除非实际违反已确认验收标准 |

缺少必需的真实测试证据应记为未完成验证，不把它伪装成代码已证实出错。无法运行当前必需验证时，该阶段保持未验收。

## 4. 避免反复打回

- 开发和审查使用同一任务、规格、契约及完成条件；模型偏好不增加新需求。
- 格式、静态检查可由项目工具稳定处理；不将个人风格偏好升级为架构缺陷。
- 结构调整或新增依赖须说明当前具体问题和收益；不以未来可能扩展为由要求重构。
- 修复后核对原问题及受影响路径；新增发现需提供独立证据，不能只是换一种说法重复已解决问题。
- 修复争议先查代码、最小复现与标准；未达成一致的问题写记录，由项目负责人根据证据决定。

## 5. 审查输出

1. 对象与范围：任务、分支、base/target commit，是否包含未提交 diff。
2. 结论：有阻断问题 / 无有据阻断问题 / 尚缺必需证据。
3. 发现：按严重程度排列；没有则写无，建议另列。
4. 验证：实际执行项、已查证据、未执行项和原因。
5. 下一步：最小修复、需要补齐的证据或可交接动作。

审查结论与发行决定分别记录，不因“review 无发现”自动宣称应用验收、Windows 安装或全部用例通过。
